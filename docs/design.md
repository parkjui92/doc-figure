# 설계 기록

왜 이렇게 만들었는지에 대한 기록. 고치려는 사람이 같은 함정을 다시 밟지 않도록.

## 1. 왜 코드가 그리는가

이미지 확산모델은 한글 라벨·정확한 수치·격자 정렬을 **반드시** 틀린다. 프롬프트를 아무리 다듬어도 못 넘는 구조적 한계다. 게다가 한 곳을 고쳐 달라고 하면 다른 곳이 깨진다.

> **2026-09 갱신** — 최신 GPT Image(2.5 세대)는 실측에서 한글 라벨을 틀리지 않았다(§10). 그래도 이 절의 결론은 유지한다. "확률적으로 드물다"와 "경로가 없다"는 다르고, 문서 그림에는 후자가 필요하다.

그래서 텍스트를 **spec에 쓴 원문 그대로 DOM에 배치**한다. 모델이 글자를 "그리는" 단계가 없으므로 글자 깨짐이 *구조적으로 불가능*해진다. 확률적으로 드물어지는 게 아니라 경로 자체가 없다.

## 2. 왜 HTML이 기본 경로인가

원래 이 도구는 파이썬 스크립트였다. spec → HTML → 헤드리스 크롬 → PNG.

그런데 그 중간 산출물인 HTML이 이미 **자기완결**이었다. 파이썬은 그것을 크롬에 먹여 스크린샷을 뜰 뿐이다. 그렇다면 스킬이 HTML을 직접 쓰면 파이썬도 크롬도 필요 없다.

이 발견 하나로 진입 장벽이 사라졌다. 공개 저장소에서 "먼저 이걸 설치하세요"는 대부분의 사람을 돌려보낸다.

파이썬 경로는 남겼다. 여러 장을 반복해 뽑고 `--verify`로 검증할 때는 자동화가 값어치를 한다.

## 3. 왜 아이콘을 뺐는가

이전 버전에는 이미지 모델로 만든 단색 픽토그램 10종이 있었다.

문제는 아이콘이 PNG라는 점이었다. HTML에 넣으려면 base64로 바꿔야 하고, 그건 파이썬 없이는 못 한다. 즉 **설치 0 경로에서만 아이콘이 빠져** 두 경로의 결과물이 달라진다.

같은 spec이 환경에 따라 다른 그림을 내는 것은 "스타일 고정"이라는 이 도구의 전제와 어긋난다. 템플릿 11종 중 아이콘을 쓰는 건 둘뿐이고 둘 다 없으면 번호·텍스트로 안전하게 퇴화하므로, 빼는 쪽이 일관성과 단순성을 동시에 얻었다.

부수 효과가 컸다 — **외부 API 의존이 0**이 됐다. 키도, 결제 계정도, 요금도 없다.

직접 만든 아이콘을 쓰려는 사람을 위해 `--icons <디렉터리>` 옵션만 남기고 자산은 넣지 않았다.

## 4. 왜 프리셋이 토큰 값만 바꾸는가

프리셋은 CSS 커스텀 속성 38개의 값 묶음이다. 템플릿은 `var(--토큰)`만 쓴다.

**토큰 이름을 프리셋마다 다르게 두면 조용히 깨진다.** 어떤 템플릿이 없는 토큰을 참조하면 그 자리만 브라우저 기본색으로 렌더되고, 아무도 알아채지 못한 채 문서에 들어간다. 오류도 경고도 없다.

그래서 `selftest.sh`가 프리셋 간 토큰 이름 집합이 완전히 같은지 매번 검사한다. 이름을 추가하려면 3벌 전부에 추가해야 한다.

같은 이유로 템플릿의 **하드코딩된 색을 전부 제거**했다. 개발 중 9곳이 발견됐고, 그중 하나 때문에 `mono-formal`(무채색) 프리셋에서 표 헤더 하나만 파랗게 남아 있었다.

`--font`는 프리셋 불변으로 뒀다. 폰트 폴백을 프리셋마다 다르게 두면 특정 프리셋에서만 글자가 깨지는데, 재현도 원인 추적도 어렵다.

## 5. `--verify`가 잡지 못하는 것

`--verify`는 spec의 모든 문자열이 렌더 결과 DOM에 실재하는지 대조한다. 글자 깨짐은 이걸로 잡힌다.

**그러나 "그림이 멀쩡한가"는 잡지 못한다.** 텍스트의 *존재*만 확인하기 때문이다.

개발 중 실제로 겪었다. `pipe-mapping`으로 예시를 만들었더니 한 레인의 병목 라벨 둘이 가로로 완전히 겹쳐 읽을 수 없었는데, `--verify`는 통과했다. 두 문자열 모두 DOM에 있었으니까.

두 가지로 대응했다.

1. 템플릿에 라벨 단 분리(`_lane`)를 넣어 겹침을 풀 수 있게 했다 — 예시만 손보면 이용자가 같은 함정을 밟는다
2. 문서 곳곳에 **결과를 눈으로 확인하라**고 명시했다

자동 검증을 신뢰하되, 그것이 무엇을 보지 못하는지도 함께 적어 두는 게 맞다고 판단했다.

## 6. 왜 `pipe-mapping`의 어휘를 바꿨는가

이 템플릿은 원래 특정 작업에서 나왔고, 데이터 키가 `country`·`device`로 박혀 있었다. 렌더 결과는 범용이었지만 spec을 쓰려면 "국가"와 "장치"라는 남의 맥락을 통과해야 했다.

`lane`·`node`로 일반화했다. 렌더 결과는 동일하고 키 이름만 바뀌었다.

## 7. 후방호환을 어떻게 지켰는가

이 저장소는 기존 도구에서 갈라져 나왔다. 엔진 경로 변경·프리셋 도입·하드코딩 색 토큰화까지 손댔으므로, 기존 spec이 예전과 같은 그림을 내는지 확인해야 했다.

동일한 spec 6종을 구엔진과 신엔진에 각각 넣고 **PNG를 바이트 단위로 비교**해 6/6 동일을 확인했다. 하드코딩 색을 토큰화할 때 `gov-navy`에는 원래 hex를 그대로 넣은 것도 이 때문이다 — 근사값으로 바꿨다면 미세하게 달라졌을 것이다.

"바뀐 게 없다"는 주장 대신 비교 결과를 남긴다.

## 8. 왜 형태 토큰을 더했는가 (v1.1)

사용자 피드백: "스타일이 너무 비슷하다."

원인을 뜯어 보니 셋이었다.

1. **프리셋이 색만 바꿨다.** 토큰 38개 중 형태는 반경 3개와 그림자 하나. `gov-navy`와 `accent-plan`을 겹치면 네이비 명도만 달랐다
2. **생김새가 템플릿에 박혀 있었다.** 가운데 굵은 제목 + 점 달린 장식선, 칠한 머리 띠, 둥근 카드, 원형 뱃지가 11종 모두에 하드코딩. 프리셋으로는 못 건드리는 층이었다
3. **규칙이 다양성을 막았다.** "안 맞으면 가장 가까운 템플릿에 억지로" + 기본 프리셋 쏠림

색 프리셋을 더 만드는 것으로는 2번이 안 풀린다. 그래서 **생김새 자체를 토큰으로 뺐다** — 제목(글꼴·정렬·장식선·밑줄·크기·자간), 캡션 정렬, 강조 상자의 칠함/외곽선, 카드 바탕, 뱃지 모양, 칩 둥글기, 바탕 패널, 줄바꿈 방식. 19개.

### 외곽선 강조를 레이아웃 변화 없이

강조 상자를 "칠함 ↔ 외곽선"으로 바꾸려면 테두리가 필요한데, `border`를 더하면 상자 크기가 변해 기존 그림이 픽셀 단위로 흔들린다. **`box-shadow: inset 0 0 0 2px`** 로 그렸다. 레이아웃에 영향이 없고, 기본값 `0 0 0 0 transparent` 는 아무것도 그리지 않는다.

같은 이유로 `--shadow: none` 을 쓸 수 없게 됐다. 템플릿이 `box-shadow: var(--strong-ring), var(--shadow)` 로 목록을 합치는데, 목록에 `none`이 끼면 **선언 전체가 무효**가 되어 외곽선까지 사라진다. `mono-formal` 의 그림자를 `0 0 0 transparent` 로 바꾼 이유다.

### 하드코딩 반경의 발견

토큰화하면서 템플릿 곳곳에 `border-radius: 10px / 12px / 14px / 20px` 가 박혀 있는 것을 찾았다. `mono-formal`(반경 4px)에서도 이 상자들은 둥글게 나오고 있었다. 전부 `--radius-box` 기준 상대값(`calc(var(--radius-box) + 2px)`, `max(0px, calc(var(--radius-box) - 2px))` …)으로 바꿨다. 같은 과정에서 논증 도해 중심 상자의 **남색 그림자**(`rgba(18,36,91,.25)`)가 무채색 프리셋에 새어 나가던 것도 잡았다 — 6자리 hex만 찾던 자체검사의 사각이었다.

### 후방호환

기본값을 v1.0 모양과 같게 잡고, 변경 전후로 11종 × 4벌(gov-navy·mono-formal·accent-plan·로컬 변형 1)을 렌더해 픽셀 비교했다. **`gov-navy` 계열 22장은 픽셀 동일.** `mono-formal`·`accent-plan` 18장은 달라졌는데, 전부 위 반경·그림자 누수를 고친 결과이며 육안으로 확인했다.

## 9. 왜 자유 도식을 열었는가 (v1.1)

v1.0은 "11종에 안 맞으면 가장 가까운 것에 재구성, 즉석 템플릿 금지"였다. 스타일 고정을 지키려는 규칙이었지만, 순환 구조를 일렬 프로세스로 그리면 되먹임이라는 핵심이 사라진다. **모양이 뜻을 바꾸는 경우**에는 억지로 끼우는 쪽이 더 나쁘다.

그래서 문을 열되 스타일 고정의 두 기둥은 지켰다.

- **색은 프리셋에서만** — `freeform` 템플릿이 토큰만 쓰는 부품 클래스(`ff-*`, SVG `s-*`/`t-*`)를 제공하고, `--verify` 가 본문의 `#hex`·`rgb()`·`hsl()` 을 적발한다 (exit 3)
- **글자는 DOM 대조** — 본문 마크업에서 태그를 걷어낸 글자 조각까지 대조한다

제목·부제·캡션은 다른 템플릿과 같은 형태 토큰을 따르므로, 자유 도식도 같은 문서의 다른 그림과 한 집안으로 보인다.

## 10. 왜 이미지 모델 경로를 다시 붙였는가 (v1.1)

§3에서 아이콘 레이어를 뺀 것은 "설치 0 경로와 결과가 갈린다"는 이유였다. 이번에 붙인 이미지 모델 경로는 **처음부터 별도 경로**로 둔다 — 기본 경로의 결과를 바꾸지 않는다.

계기는 실측이었다. 같은 4단계 프로세스 프롬프트로 gpt-image-2 와 gpt-image-2.5-sunburst 를 비교했더니 둘 다 한글 18개를 정확히 그렸고, 2.5-sunburst 는 시간 1/3, 출력 토큰 1/4이었다. 이어 조직도·히트맵·간트(코드 렌더 참조)까지 라벨 103개 전부 정확.

설계 결정:

- **같은 spec, 같은 프리셋.** 프롬프트의 내용은 spec에서, 스타일(팔레트 hex·모서리·그림자·강조 방식·제목 글꼴)은 프리셋 토큰에서 자동으로 뽑는다. 사람이 프롬프트를 손으로 쓰면 그림마다 톤이 흔들린다
- **넣을 글자를 전수로 준다.** "이것만, 글자 그대로". 이 목록이 곧 OCR 대조표다
- **`--from-render`.** 코드 렌더를 참조 이미지로 넘겨 "배치·글자는 그대로, 마감만" — 좌표가 중요한 간트·히트맵에서 배치 정확도를 코드 수준으로 끌어올린다
- **`--fix`.** 틀린 곳 하나 때문에 전체를 다시 뽑으면 다른 곳이 틀릴 수 있다. 편집 API로 그 부분만 고친다. 실측: 히트맵 3단계 색 교정에서 지정한 칸만 바뀌고 글자 39개는 그대로
- **모델 자동 선택.** 이미지 모델은 몇 달 단위로 바뀐다. id를 박아 두면 낡는다. API 목록에서 최신 버전을 고르고(정밀 변형 우선), 실제로 쓴 id를 메타에 남긴다

### OCR — tesseract 에서 macOS Vision 으로

처음엔 tesseract(kor)로 대조했는데 **멀쩡한 "9월"을 누락으로 판정**할 만큼 오탐이 많았다(간트 24/44, 히트맵 23/39). 확대·대비 보정도 효과가 없었다 — 색 바탕 위 작은 한글에 약하다. macOS 내장 Vision 문자인식으로 바꾸자 43/44, 37/39, 20/20. 남는 것은 ▲·→ 같은 기호였다. Vision은 Swift 소스를 스크립트에 품고 최초 1회 `swiftc`로 컴파일해 캐시한다. macOS가 아니면 tesseract로 떨어진다.

**그래도 OCR은 1차 거름망일 뿐이다.** 최종 판정은 이미지를 직접 읽는 것이다. SKILL.md가 "육안 대조 전에는 완성이라 말하지 않는다"를 규칙으로 둔 이유.

## 11. 왜 색보다 형태인가 (v1.2)

v1.1에서 프리셋이 생김새까지 바꾸게 했지만, 사용자의 다음 말은 "색깔만 바꿀 게 아니라 다양한 도식의 형태로 의도를 설명하게"였다. 맞는 지적이었다. 11종은 대부분 **상자와 화살표**의 변주라, 프리셋을 아무리 바꿔도 "순환"이나 "겹침"이나 "숨은 것이 더 크다" 같은 관계는 그릴 수 없었다. 그런 관계는 결국 가장 가까운 상자 그림으로 뭉개졌다.

### 모양은 주장이다

순환도는 되먹임을, 피라미드는 위계를, 벤은 겹침을, 폭포는 합계가 맞음을 주장한다. 그래서 형태 선택을 스타일 문제가 아니라 **논증 문제**로 다뤘다. `form-catalog.md` 에 판정표(본문 신호 → 관계 → 형태)와 함께 "모양이 하는 주장 점검표"를 둔 이유다. 되먹임이 없는데 순환도를 쓰면 그림이 거짓말을 한다.

그 주장 중 코드로 검사할 수 있는 것은 검사한다 — 폭포 차트는 끝값이 시작+증감과 다르면 렌더를 멈춘다.

### 왜 14종을 템플릿 하나에

기존 11종은 파일 하나에 템플릿 하나였다. 14종을 같은 방식으로 두면 머리·캡션·보조 함수가 14벌 복제된다. `forms.html` 한 파일에 형태별 렌더 함수를 두고 `form` 으로 고르게 했다. 사용자는 `"template": "venn"` 이라고 쓰고, 렌더러가 `forms` 로 돌린다. 설치 0 경로(스킬이 HTML을 직접 쓰는 경로)도 파일 하나만 읽으면 된다.

### 도형은 SVG, 글자는 HTML

SVG `<text>` 는 줄바꿈을 못 한다. 한국어 라벨을 SVG에 넣으면 폭 계산과 줄 나눔을 직접 해야 하고, 어절 경계를 틀리기 쉽다. 도형·선은 SVG에 그리고, 글자는 그 위에 절대배치 HTML로 얹었다. 줄바꿈은 브라우저가 `word-break: keep-all` 로 한다. 스윔레인·로직 트리처럼 상자 크기에 따라 선을 이어야 하는 형태는 배치가 끝난 뒤 상자를 재서 선을 긋는다.

### 왜 프롬프트와 도식을 한 벌로

이미지 모델 경로를 붙인 뒤 생긴 질문은 "그래서 어느 쪽을 쓰나"였다. 답은 **둘 다 같은 spec에서 나오게 하고 나란히 보이는 것**이었다. 코드 도식은 정확함과 수정 용이성을, 프롬프트는 이미지 모델이나 디자이너에게 넘길 설계서를 준다. 둘이 같은 의도 문장·같은 프리셋에서 나오므로 서로 어긋나지 않는다. `figure_pack` 의 카드 페이지는 그 둘과 후보 간 비교를 한 화면에 놓는다 — 형태를 고르는 것은 결국 사람이 보고 하는 일이기 때문이다.

### 실측

같은 "성과 활용이 낮다"를 피시본·빙산·로직 트리로 묶어 `--gpt` 로 돌렸다. 세 장 모두 한글 라벨 전수 정확(18/18, 12/12, 16/16, macOS Vision 대조 + 육안), 장당 27~28초. 모델이 목록에 없는 ①②③ 번호를 세 장 모두 덧붙였다 — 번호는 순서·우선순위를 암시하므로 프롬프트 금지 절에 명시했다.
